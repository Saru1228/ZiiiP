# 001 小实验报告：这条路值不值得继续走？

日期：2026-10-08

更新：后续已经继续排查并修复了这里提到的回灌差异，详见 `GPTreview/002.md`。

## 先说结论

值得继续走。

我已经在本地电脑上跑通了一个小实验：不用换 Linux 电脑，直接用现在这台 Windows 机器里的 WSL，就能读取 `enwik9`，运行压缩程序，并把中间结果导出来分析。

但这次实验只能说明“路能走”，还不能说明“这个新想法一定能压得更好”。

更直白地说：

- 电脑环境：基本可用。
- 数据读取：可用。
- 压缩程序：能跑。
- 中间概率数据：能导出。
- Python 分析：能跑。
- 低秩残差这个想法：有一点可观察信号，但现在还不能下结论。

## 这次我具体做了什么

我从 `enwik9` 里取了前 1MB 数据，做了一次小规模压缩测试。

原始数据大小：

```text
1,000,000 bytes
```

压缩后的大小：

```text
175,129 bytes
```

这说明原程序在本地确实能正常工作，不只是“能编译”，而是真的能处理数据并生成压缩结果。

同时，我还让程序额外保存了几类中间文件：

- PPMD 看到的 token 序列
- PPMD 给出的概率
- Transformer 给后续压缩模块的概率

这些文件后面就是我们做实验的原材料。

## 最重要的好消息

中间数据的尺寸是完全对得上的。

这点很关键，因为如果中间数据少了一截、错位了、或者维度不对，后面所有分析都会没有意义。

这次得到：

```text
token 数量：600,742
每个 token 有 205 个概率
每个概率用 2 bytes 保存
```

所以理论文件大小应该是：

```text
600742 * 205 * 2 = 246,304,220 bytes
```

实际导出的 PPMD 概率文件和 Transformer 概率文件都是：

```text
246,304,220 bytes
```

这说明保存出来的数据结构是完整的，第一道大坑已经避开了。

## 我又做了一个回灌测试

这一步很重要。

我们的目标不是只把概率导出来看看，而是希望以后可以这样做：

```text
原程序导出概率
   -> 我们在 Python 里改概率
   -> 再把改过的概率交回压缩程序
   -> 看压缩结果有没有变好
```

所以我测试了一下：把刚刚保存出来的 Transformer 概率重新喂回压缩程序。

结果是：能跑完。

回灌后的压缩文件大小是：

```text
175,282 bytes
```

它和原始 Transformer 运行结果相比，多了：

```text
153 bytes
```

这个差异不大，但它很重要。

它说明这条“导出 -> 修改 -> 回灌”的路已经能走，但还没有做到完全一模一样复现。下一步必须先解释这 153 bytes 是哪里来的，否则后面我们改模型时，很难判断压缩结果的变化到底来自我们的改动，还是来自这个接口本身的误差。

## 这次对核心想法有什么启发？

你的大方向是：

```text
PPMD 已经给了一个很强的基础预测，
Transformer 可能不需要重新学完整分布，
也许只需要学一个比较小的修正量。
```

这次我做了一个初步检查：看 Transformer 和 PPMD 之间的差异，是不是有比较集中的结构。

结果是：有一点信号。

比如：

- 第 1 个主要方向就解释了大约 40% 的差异。
- 前 16 个方向解释了大约 70% 的差异。

这说明“差异可能不是完全乱的”，低秩修正这个方向不是凭空想象。

但是，这还不是胜利。

因为我直接用这些低秩近似去打分时，结果并没有比 PPMD 更好。更关键的是，目前保存出来的 Transformer 概率并不是最终压缩器真正使用的完整预测结果，而是传给后续模块的中间结果。

所以这次只能说：

```text
这个方向值得继续查。
但现在还不能说它已经有效。
```

## 这次已经证明的事情

已经证明：

- 本地 WSL 可以继续做这个项目。
- 不一定要换 Linux 电脑。
- `enwik9` 可以被正常读取。
- 小样本压缩可以跑完。
- PPMD 概率可以导出。
- Transformer 中间概率可以导出。
- Python 能读取这些大文件并做分析。
- 概率回灌功能可以跑通。

这对项目来说是一个很重要的节点：我们现在有了一个可以反复实验的小闭环。

## 这次还没有证明的事情

还没有证明：

- 低秩残差方案真的能让压缩文件变小。
- 回灌后的结果能完全复现原始运行。
- 小样本结果能代表完整 `enwik9`。
- 最终模型变小带来的收益，能不能抵消压缩率损失。

这些都要后面继续测。

## 我建议下一步做什么

下一步不要急着改模型。

我建议先把实验管道打磨稳：

1. 先解释回灌为什么会多出 153 bytes。
2. 让“导出概率 -> 再加载概率”做到尽量严格复现。
3. 再开始替换低秩修正后的概率。
4. 最后只看一个硬指标：压缩后的文件有没有真的变小。

也就是说，下一步的目标不是追求漂亮理论，而是先把尺子校准。

只有尺子准了，后面每一次改动才知道是真的进步，还是测量误差。

## 当前判断

我的判断是：

```text
继续。
```

原因不是因为这次已经证明低秩残差有效，而是因为本地实验链路已经被打通，而且结果暴露出了一个明确的下一步问题：回灌差异。

这类问题是可以继续工程排查的，不是死路。
