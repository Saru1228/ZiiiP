# 002 回灌差异排查：153 bytes 从哪里来？

日期：2026-10-08

## 先说结论

153 bytes 的主要原因已经找到了，也已经做了本地修复。

之前的情况是：

```text
原始 Transformer 跑法：175,129 bytes
保存概率再回灌：175,282 bytes
差异：153 bytes
```

修复后，用同一个新编译出来的程序做公平对照：

```text
原始 Transformer 跑法：175,130 bytes
保存概率再回灌：175,130 bytes
差异：0 bytes
```

这说明“导出概率 -> 再加载概率 -> 重新压缩”这条实验管道现在可以复现了。

## 问题出在哪里

原程序在回灌概率时，会跳过 PPMD。

这听起来好像合理，因为 Transformer 的概率已经从文件里读出来了，不需要 PPMD 再算一次。

但实际压缩程序不是只有 Transformer 一个模块。它后面还有一组混合器，会同时看很多信号，其中也包括 PPMD 自己给出的 bit 级预测。

所以旧逻辑变成了：

```text
原始 Transformer 路径：
PPMD 仍然运行
Transformer 使用 PPMD 的信息
后续混合器也能看到 PPMD 的 bit 级信号

回灌路径：
Transformer 概率从文件读取
PPMD 被跳过
后续混合器看不到真实 PPMD 信号，只看到一个默认值
```

这就解释了为什么两边的压缩结果会差一点。

## 我做了什么修复

修复思路很简单：

```text
回灌时，Transformer 概率仍然从文件读取；
但是 PPMD 也继续运行，
这样后续混合器看到的 PPMD 信号就和原始路径一致。
```

也就是说，回灌不是为了省掉所有计算，而是为了替换 Transformer 输出。PPMD 仍然是整个压缩系统的一部分，不能随便关掉。

补丁已经实际打到本地的：

```text
fx2-cmix-transformer-v1/src/predictor.cpp
```

为了以后同步时不丢，我也把补丁保存到了主项目：

```text
patches/fx2-roundtrip-ppmd-fix.patch
```

## 修复后的验证结果

我重新编译了一个测试用 `cmix`。

因为直接 `make` 需要带两个固定参数，所以这次使用：

```text
SEED=923
UPDATE_LIMIT=3000
```

修复前后对比：

| 测试 | 压缩后大小 |
|---|---:|
| 旧回灌路径 | 175,282 bytes |
| 修复后回灌路径 | 175,130 bytes |
| 同一个新程序的原始 Transformer 路径 | 175,130 bytes |

这说明 153 bytes 的差异不是低秩想法的问题，而是实验管道本身的一个路径不一致。

现在这个不一致已经被消掉。

## 为什么和最早的 175,129 bytes 差 1 byte？

最早的 `175,129 bytes` 是之前那个旧二进制跑出来的。

这次修复后我重新编译了一个测试二进制。用这个新二进制跑原始 Transformer 路径，结果是 `175,130 bytes`；用同一个新二进制跑回灌路径，也是 `175,130 bytes`。

所以当前更重要的对比是：

```text
同一个程序下，原始路径和回灌路径一致。
```

这比和旧二进制比较更有意义。

## 这一步意味着什么

这一步非常关键。

现在我们终于有了一把更可靠的尺子：

```text
如果我们改了概率文件，
再回灌给压缩程序，
压缩文件大小的变化就更可能来自我们的改动本身。
```

这意味着下一步可以开始做真正的低秩替换小实验了。

## 下一步

下一步仍然先用 1MB 样本，不急着上 10M。

建议做：

1. 用现有 PPMD 概率和 Transformer downstream 概率生成一个低秩替代概率文件。
2. 把这个替代概率文件回灌给压缩程序。
3. 比较压缩大小是否低于 `175,130 bytes`。

如果 1MB 上完全没有正向信号，再扩大到 10M 意义不大。

如果 1MB 上有正向信号，再进入 10M 验证阶段。
