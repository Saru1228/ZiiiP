# 003 低秩替代小实验：1MB 上有没有正向信号？

日期：2026-10-08

## 先说结论

这次没有跑出正向结果。

在 1MB 小样本上，简单的低秩替代概率没有压过完整 Transformer。

不过这不是坏消息。它至少告诉我们：最朴素的“直接做 PCA，然后拿低秩重构概率回灌”的办法，不值得直接扩大到 10M 或 100M。

## 测试前提

上一轮已经修好了回灌差异。

现在同一个新编译程序下：

```text
原始 Transformer 路径：175,130 bytes
保存概率再回灌：175,130 bytes
```

这说明实验尺子已经对齐，可以开始比较替代概率文件。

## 这次测试了什么

我生成了三个低秩版本：

```text
rank 1
rank 16
rank 64
```

可以粗略理解为：

- rank 1：只保留最主要的一条修正方向。
- rank 16：保留一小组主要修正方向。
- rank 64：保留更多修正方向，但仍比完整 205 维分布小。

另外，我还做了一个对照：

```text
直接把 PPMD 概率当作 downstream 概率回灌
```

这个对照可以帮助判断低秩修正到底有没有比“只靠 PPMD”更好。

## 结果

基线：

```text
完整 Transformer：175,130 bytes
```

测试结果：

| 方案 | 压缩后大小 | 比完整 Transformer 多多少 |
|---|---:|---:|
| 完整 Transformer | 175,130 bytes | 0 |
| 保存后再回灌的 Transformer | 175,130 bytes | 0 |
| 直接回灌 PPMD 概率 | 176,338 bytes | +1,208 |
| rank 1 低秩替代 | 176,460 bytes | +1,330 |
| rank 16 低秩替代 | 176,361 bytes | +1,231 |
| rank 64 低秩替代 | 176,294 bytes | +1,164 |

## 怎么解读

第一，完整 Transformer 仍然明显最好。

第二，低秩版本目前没有打过完整 Transformer。

第三，rank 越高，结果略微变好：

```text
rank 1:  176,460
rank 16: 176,361
rank 64: 176,294
```

这说明低秩修正确实保留了一部分有用信息，但保留得还不够，或者方法太粗糙。

第四，rank64 比直接用 PPMD 概率略好：

```text
PPMD:   176,338
rank64: 176,294
```

差距只有 44 bytes，很小，但方向是对的。

## 这说明下一步不应该是什么

我不建议现在立刻跑 10M 或 100M。

原因是：1MB 上最朴素版本已经没有打过完整 Transformer。直接扩大样本，很可能只是更慢地确认同一个负面结果。

## 更合理的下一步

下一步应该改方法，而不是先改规模。

我建议下一个方向是：

```text
不要直接用全局 PCA 低秩重构。
改成“带权重的混合”或“轻量 affine 修正”。
```

更具体一点：

1. 保留 PPMD 概率作为基础。
2. 不直接完全替换成低秩重构结果。
3. 尝试一个混合系数：

```text
新概率 = PPMD 基础 + 一点点低秩修正
```

也就是先测试：

```text
alpha = 0.1, 0.2, 0.4, 0.8
```

看轻量修正是否能比“纯 PPMD downstream”更好，甚至接近完整 Transformer。

## 当前判断

这次结果把路线收窄了。

可以继续，但不要盲目扩大数据。

当前最有价值的问题变成：

```text
低秩方向本身是否有用？
如果有用，应该用多大力度加到 PPMD 上？
```

所以接下来应该做 `alpha` 混合实验，而不是直接上 10M。
