# 006 继续尝试后的结果：local 和 top-k 没有超过 global log-ratio

日期：2026-10-08

## 先说结论

我继续按 `004.md` 往下做了三件事：

1. 分析 Transformer 到底在哪些位置可能有帮助。
2. 测试按 PPMD 不确定性分桶的 local PCA。
3. 测试只修正 top-k 候选字符的 sparse correction。

结果是：

```text
global log-ratio PCA 仍然是目前最好的方向。
```

之前最佳：

```text
global log-ratio rank64 alpha0.8
= 176,064 bytes
= 追回 22.7%
```

这次 local PCA 和 top-k 都没有超过它。

## Gain analysis：Transformer 更像是在困难位置有用

我先看每个位置上：

```text
Transformer 给真实字符的概率
相对
PPMD 给真实字符的概率
```

得到一个大致趋势：

```text
PPMD 越不确定，Transformer-like correction 越可能有帮助。
```

用 PPMD entropy 分 4 桶：

| 桶 | 含义 | 正收益比例 |
|---|---|---:|
| Q1 | PPMD 最确定 | 18.3% |
| Q2 | 较确定 | 28.4% |
| Q3 | 较不确定 | 37.4% |
| Q4 | 最不确定 | 35.4% |

这个结果说明：用 PPMD 的不确定性来分桶，有一定理由。

但要注意：这个 gain 只是诊断。最终还是要看压缩文件大小。

## Local PCA：按 entropy 分桶没有赢

接着我做了：

```text
按 PPMD entropy 分成 4 个桶
每个桶单独做 PCA
```

`004.md` 里最关键的比较是：

```text
global rank32
vs
4 buckets × local rank8
```

结果：

| 方法 | 压缩大小 | 追回比例 |
|---|---:|---:|
| global rank32 alpha0.6 | 176,205 | 11.0% |
| 4×local rank8 alpha0.6 | 176,281 | 4.7% |
| 4×local rank16 alpha0.6 | 176,270 | 5.6% |

结论：

```text
entropy local PCA 没有超过 global PCA。
```

也就是说，至少用 PPMD entropy 这个分桶方式，不能证明 residual 是局部低维结构。

## Top-k sparse correction：也没有赢

然后我测试：

```text
只修正 PPMD 概率最高的 top-k 个候选字符
```

结果：

| top-k | 压缩大小 | 追回比例 |
|---:|---:|---:|
| 4 | 176,571 | -19.3% |
| 8 | 176,516 | -14.7% |
| 16 | 176,428 | -7.5% |
| 32 | 176,327 | 0.9% |
| 64 | 176,234 | 8.6% |
| 完整 205 维 rank64 | 176,064 | 22.7% |

结论：

```text
Transformer 的有用修正不只在 top 几个候选字符上。
```

小 top-k 甚至会让压缩变差。

这说明中低概率区域、尾部概率质量的移动也重要。

## 当前总排名

目前最重要的结果：

| 方法 | 压缩大小 | 追回比例 |
|---|---:|---:|
| 完整 Transformer | 175,130 | 100.0% |
| global log-ratio rank64 alpha0.8 | 176,064 | 22.7% |
| global log-ratio rank32 alpha0.6 | 176,205 | 11.0% |
| sparse top64 | 176,234 | 8.6% |
| local entropy rank16 alpha0.6 | 176,270 | 5.6% |
| raw PCA rank64 | 176,294 | 3.6% |
| PPMD 对照 | 176,338 | 0.0% |

## 怎么理解

现在可以说：

```text
log-ratio 坐标系是有用的。
```

但还不能说：

```text
entropy 分桶有用。
```

也不能说：

```text
只修正 top-k 就够了。
```

目前最合理的判断是：

```text
Transformer 相对 PPMD 的修正，
确实有一部分低维结构，
但这个结构不是简单的 entropy-local，
也不是简单的 top-k sparse。
```

## 下一步建议

现在有两个合理方向。

方向 A：测试多个 1MB slice

目的：

```text
确认 global log-ratio rank64 的 22.7% 不是当前这个 1MB 片段的偶然。
```

方向 B：做 coding-aware oracle low-rank

目的：

```text
判断 PCA 的目标函数是不是错了。
```

PCA 追求的是：

```text
重构误差小
```

但压缩真正关心的是：

```text
真实字符概率高
```

所以可能需要一个直接面向 coding loss 的 oracle 实验。

我的建议：

```text
先做 coding-aware oracle low-rank。
```

因为它能回答一个更核心的问题：

```text
低秩表示本身到底有没有足够容量？
```

如果 oracle 条件下都追不回来更多 gap，那就不值得继续研究怎么预测 latent。
